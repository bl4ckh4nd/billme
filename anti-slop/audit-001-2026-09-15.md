# antislop audit 001, billme monorepo

- Date: 2026-09-15
- Mode: 2 (AFTER). Read-only audit of the existing product. No file was modified.
- Filter: `antislop` (core, rules R-01..R-38, C-1..C-5) plus `antislop-ui` (UI/visual depth).
- Direction: `DESIGN.md` exists at repo root, so R-37 is satisfied at the document level. It declares tokens, radius scale, typography, layering and elevation rules, but declares **no ENERGY / RHYTHM / MOTION dials** (see F-046).

## 1. Scope and method

Surfaces scanned (563 source files under `apps/*`, `packages/*`, excluding `node_modules`, `dist`, `out`, `release`, `coverage`, `.test-logs`, `.artifacts`):

| `apps/pro-desktop` | 183 | Pro Electron app: same shell plus accounting pages |
| `packages/desktop-renderer` | 48 | Shared Lite+Pro views (18 rendering components, the highest-traffic surface) |

Methods: a mechanical census run by the orchestrator (regex census with per-file counts, contrast computed from token hex, compiled-CSS inspection), then nine parallel read-only semantic audits, one per surface, each confirming patterns in context and tracing import graphs where a claim depended on reachability. Every finding below cites a file and a line. Contrast ratios are computed from the declared token hex values, not sampled from rendered pixels (see Gaps).

Priority follows the rule tier, per the antislop mode-2 contract: **Hard Gate = HIGH**, **Purpose-Gate = MEDIUM**, **Quality Locks = LOW**.

## 2. Verdict summary

| Tier | Findings |
| --- | --- |
| HIGH (Hard Gate) | 16 |
| MEDIUM (Purpose-Gate) | 18 |
| LOW (Quality Locks) | 17 |
| Total | 51 |

Two further entries (F-022, F-023) record PASS verdicts rather than findings, and Group I records the clean checks.

Four structural facts dominate the whole audit:

1. **The app surface is not on tokens.** 846 untokenized gray/slate utility matches in `packages/desktop-renderer`, 290 in `apps/pro-desktop/components`, 238 in `apps/desktop/components`, versus 144 / 39 / 28 token usages in the same trees. `packages/accounting-ui-pro` is the opposite (583 token uses), so the correct pattern already exists in-repo. `DESIGN.md` bans default gray/slate utilities in app-shell chrome, so this is drift, not a design decision.
2. **Pro and Lite duplicate six real components.** 23 of the 42 Pro component files are byte-identical one-line re-export shims (nothing to fix). Six more are near-identical copies of real code (`DashboardViews` 1521/1519 lines, `DashboardLayout` 461/471, `StatisticsView` 354/359, `ErrorBoundary` 231/231, `OnboardingWizard`, `InvoiceEditor`). Every fix lands twice until one owner exists.
3. **Motion is unguarded and global.** `apps/desktop/index.html` and `apps/pro-desktop/index.html` define `fadeInUp` / `fadeInScale` / `.animate-enter` / `.animate-scale-in` / `.premium-hover` in a raw `<style>` block. Usage: 60 `animate-enter`, 30 `animate-scale-in`, 12 `premium-hover`, 103 `transition-all`, with **one** `prefers-reduced-motion` block in the entire repo (landing page only). Both classes start at `opacity: 0`, so reduced-motion handling is also a correctness concern.
4. **`.dark:` utilities are live and half-applied.** Tailwind is v4.1.18 with no `tailwind.config.*` and no `@custom-variant dark` anywhere, so `dark:` compiles to `@media (prefers-color-scheme: dark)`. Compiled proof: `apps/pro-desktop/dist/assets/index-JROdjHev.css` ships 13 `dark:*` utilities inside that media query (`.dark\:bg-gray-900`, `.dark\:bg-gray-700`, `.dark\:text-gray-100`, ...). Those are used only in `DashboardViews.tsx` (Lite and Pro, ~12 sites each), so a user whose OS is dark gets those cards and modals in gray-900 while the rest of the app stays light.

## 3. Findings

Convention: each finding is one pattern, one rule, evidence, and a one-line fix direction. Groups A to H are the fix phases of section 6.

### Group A: Honesty (fabricated content reaching users)

**F-001** `R-38` `R-17` **HIGH**. `MOCK_SETTINGS` is the unconditional runtime fallback for the user's own settings.
Evidence: `packages/desktop-renderer/src/components/SettingsView.tsx:42-43` `useState<AppSettings>(loadedSettings ?? MOCK_SETTINGS)`; `InvoicesView.tsx:185`, `InvoiceDocumentEditor.tsx:58` `settings={(settings ?? MOCK_SETTINGS)}`, `apps/desktop/router.tsx:166`, `apps/pro-desktop/router.tsx:173`, `apps/desktop/components/DashboardViews.tsx:153`, `apps/pro-desktop/components/DashboardViews.tsx:153`, `StatisticsView.tsx:28` (both apps).
Payload: `packages/desktop-services/src/mockData.ts:32-44` `name: 'Mustermann GmbH'`, `owner: 'Max Mustermann'`, `street: 'Musterstraße 123'`, `iban: 'DE12 1005 0000 1234 5678 90'`, `taxId: '12/345/67890'`, `registerCourt: 'Amtsgericht Charlottenburg HRB 12345'`; `:109` `monthlyRevenueGoal: 30000`.
Why it is a violation: `useSettingsQuery` returns `data: undefined` while loading and on error (`hooks/useSettings.ts:7-12`, no error branch), so this fallback is reached on every first paint and persists after any settings failure. `packages/desktop-utils/src/placeholders.tsx:211-235` resolves `{{my.name}}`, `{{my.address_line}}`, `{{my.iban}}`, `{{my.taxId}}` from exactly those fields, so a fabricated legal and bank identity can render inside a user's invoice. `DEFAULT_SETTINGS` (`mockData.ts:124-199`) is the honest neutral seed that exists for this purpose.
Fix: delete every `?? MOCK_SETTINGS` on the settings path; gate the affected views on the settings query state.

**F-002** `R-27` `R-38` **HIGH**. A failed or slow settings query is indistinguishable from real data, and there is no error state.
Evidence: `SettingsView.tsx:41-43` destructures `data` only; the form state is seeded from the mock fallback and stays there on error; `InvoicesView.tsx:185`, `DashboardViews.tsx:153`, `StatisticsView.tsx:28` have the same shape.
Fix: settings loading skeleton plus an error state that names the cause and offers retry; no fabricated prefill.

**F-003** `R-38` **HIGH**. The public demo (`demo.getbillme.com`) serves invented customers, invoices, balances and IBANs through the real product UI with no in-app label.
Evidence: `apps/demo/src/main.tsx:8` mounts the real renderer with `demoHttpApi` and no demo flag; `apps/demo/src/worker.ts:66-67` `private invoke = createMockInvoke();`; seed data in `packages/desktop-services/src/mockData.ts` (`Mustermann GmbH`, `Musterfirma GmbH`, `balance: 124500.00`). The only user-visible signal is `<title>Billme Demo</title>` (`apps/demo/index.html:6`).
Fix: a persistent "Demo-Daten, nicht gespeichert" banner in the demo build.

**F-004** `R-38` **MEDIUM**. The dunning preview fabricates the customer and sender identity where the real settings are in scope.
Evidence: `packages/desktop-ui/src/components/DunningLevelPreviewModal.tsx:22-32` `.replace(/%C/g, 'Mustermann GmbH')`, rendered at `:89`, `:108-111` as `kunde@mustermann.de`, `Musterstraße 123`, `12345 Musterstadt`, `info@example.com`.
Fix: resolve recipient and sender from settings, or label the sample values as stand-ins where they render.

**F-005** `R-38` **MEDIUM**. Mock bank transactions attribute fabricated payment histories to identifiable real companies.
Evidence: `packages/desktop-services/src/mockData.ts:461-470` `counterparty: 'Telekom Deutschland'`, `'Adobe Systems'`, `'DB Vertrieb GmbH'`, `'Finanzamt Berlin'` with plausible amounts, dates and `status: 'booked'`.
Fix: replace with clearly synthetic counterparties consistent with the `Musterfirma GmbH` convention in the same file.

**F-006** `R-38` `R-23` **LOW**. The first-run onboarding asks for the user's identity while showing a fake one as the placeholder.
Evidence: `packages/desktop-ui/src/components/BusinessOnboarding.tsx:635,645,656,689,926,935,971` `placeholder="Muster GmbH"`, `"Max Muster"`, `"Musterstrasse 12"`, `"kontakt@muster.de"`.
Fix: instructive hints ("z. B. deine Firma") instead of a fake identity.

**F-007** `R-09` `R-31` **LOW**. A badge that marks no state.
Evidence: `apps/desktop/components/DashboardViews.tsx:1379` (and the Pro twin) renders `Aktiv` unconditionally for every account, with no active flag behind it, while the same card already shows the real transaction count.
Fix: derive it from real state or drop it.

### Group C: Motion

**F-024** `R-19` **MEDIUM**. Template animation stack applied globally, with no `prefers-reduced-motion` guard anywhere except the landing page.
Evidence: declarations in `apps/desktop/index.html:57-105` and the Pro twin (`.animate-enter` = `fadeInUp` with a 20px translate and 0.98 scale, `.animate-scale-in`, `.premium-hover:hover` = `translateY(-4px)` plus `0 20px 40px -15px` shadow, `.delay-75..300`). Usage counts: 60 `animate-enter`, 30 `animate-scale-in`, 12 `premium-hover`, 103 `transition-all`. The whole `<main>` re-animates per route (`DashboardLayout.tsx:463`), every settings panel animates (`SettingsView.tsx:401,490,571,649,816,1023,1355,1541,1604,1729`), and staggered delays reach 300ms (`ClientsView.tsx:1222`). The only `@media (prefers-reduced-motion: reduce)` block in the repo is `apps/landing-page/src/index.css:148-157`; `packages/ui` primitives guard correctly with `motion-safe:` (`Button.tsx:64`, `AuthScreen.tsx:259`, `ConfirmDialog.tsx:139`, `Toast.tsx:83`) while `packages/desktop-ui/src/components/{SkeletonLoader.tsx:13,33,50, Spinner.tsx:15}` do not, and `apps/desktop/components/Titlebar.tsx:146` runs `animate-pulse` on a download icon forever.
Consequence beyond taste: both entrance classes start at `opacity: 0`, so if motion is suppressed without removing the class, content stays invisible.
Fix: move the keyframes into the token stylesheet, wrap them in `motion-safe:` with a `motion-reduce:animate-none` fallback that also resets opacity, and keep motion for modal/route entry only.

**F-025** `R-19` **MEDIUM**. Animation classes referenced but never defined, so they silently do nothing.
Evidence: `animate-in slide-in-from-right duration-300` at `ArticlesView.tsx:359,537`, `RecurringView.tsx:356`, `InvoicesView.tsx:688,754,1674,1816`; `animate-fade-in` at `DashboardViews.tsx:844,1099`; no definition in `packages/ui/styles.css`, either `index.html`, or any dependency (`tailwindcss-animate` is not installed). `apps/pro-desktop/index.html` also references an undefined `animate-fade-in`.
Fix: define them once in the token layer or delete the classes.

## 7. Decisions (approved 2026-09-15)

Answered by the product owner before any fix was applied:

1. **Scope**: full program, Phases 1 to 7.
2. **Dials**: `ENERGY 1 / RHYTHM 1 (apps) and 2 (landing page) / MOTION 1`. Recorded in `DESIGN.md`. Consequence accepted: the existing entrance animation stack (60 `animate-enter`, 30 `animate-scale-in`, 12 `premium-hover` sites) is a defect and is removed, not kept.
3. **`apps/web-pro`**: fold onto `@billme/ui` tokens; the standalone 381-line stylesheet is deleted.
4. **Lite/Pro duplication**: extract the six duplicated components into `packages/desktop-ui/src/shell/` first, before the mass edits.

Decisions taken by the orchestrator under those answers, recorded here so later work does not relitigate them:

- Two new tokens: `surface-sunken` (#f3f4f6, the app shell ground, previously raw hex) and `control-border` (#8b8b8b, 3.41:1 on white, for control outlines; `border` at 1.24:1 cannot carry a control boundary).
- `muted` darkens from #6b7280 to #676d75 so secondary copy clears 4.5:1 on `surface-sunken` (it was 4.39:1).
- The empty-value glyph is the en dash `–`, exported as `EMPTY_VALUE` / `formatEmptyValue()` from `@billme/ui`. Prose em dashes are rewritten; the character is banned.
- `EmptyState` and `ErrorState` are added to `@billme/ui`, because the audit found no shared convention and therefore 12 of 14 renderer views improvised.
- `bg-canvas` and `bg-editor-viewport` map to existing tokens (`bg-surface`, `bg-dark-1`) instead of gaining new tokens.
- The guard added in Phase 7 is `scripts/design-token-guard.mjs`, run as `pnpm check:design-tokens`, modelled on the existing `scripts/raw-sql-guard.mjs`.
